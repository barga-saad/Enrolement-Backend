2. SECURITY ARCHITECTURE
================================================================================

2.1 AUTHENTICATION & AUTHORIZATION
────────────────────────────────────

AUTHENTICATION (Who are you?):
  ✓ JWT Bearer Token from Keycloak/Auth Server
  ✓ Token validated on every request
  ✓ JwtAuthenticationFilter processes tokens
  ✓ SpringSecurityContext holds authenticated user

AUTHORIZATION (What can you do?):
  ✓ Role-Based Access Control (RBAC)
  ✓ 4 roles: PROFIL_SAISIE, PROFIL_VALIDATEUR, PROFIL_CONSULTATION, PROFIL_ADMIN_CENTRAL
  ✓ 15 permissions (database-driven, not hard-coded)
  ✓ Dynamic permission resolution via PermissionResolver
  ✓ PermissionAuthorizationFilter enforces on every request
  ✓ Multi-role users supported (both roles' permissions combined)

2.2 ROLE & PERMISSION SYSTEM
──────────────────────────────

ROLES (4 total):
  1. PROFIL_SAISIE (Data Entry Clerk)
     - Can create partners
     - Can create transfers
     - Can view own data
     - Cannot validate or approve

  2. PROFIL_VALIDATEUR (Validator)
     - Can view all partners
     - Can validate transfers
     - Can approve transactions
     - Cannot delete

  3. PROFIL_CONSULTATION (Read-Only)
     - Can view all data
     - Cannot create or modify
     - Cannot delete

  4. PROFIL_ADMIN_CENTRAL (Administrator)
     - Full system access
     - Can manage users, roles, permissions
     - Can audit all activity
     - Emergency access

PERMISSIONS (15 total, database-driven):
  Each permission has: name, endpoint, httpMethod, requiresOwnerCheck
  
  Examples:
    - CREATE_PARTNER: POST /v1/create/partners
    - UPDATE_PARTNER: PUT /v1/update/partners
    - DELETE_PARTNER: DELETE /v1/delete/partners/{id}
    - VIEW_ALL_PARTNERS: GET /v1/read/partners
    - MANAGE_USERS: POST /admin/users
    - etc.


2.3 SECURITY LAYERS
──────────────────

Layer 1: JwtAuthenticationFilter
  - Validates token signature
  - Checks token expiration
  - Extracts user claims
  - Sets SecurityContext

Layer 2: PermissionAuthorizationFilter
  - After JWT validation
  - Loads user permissions from database
  - Checks if request matches permission
  - UNION-based for multi-role users (most permissive wins)
  - Returns 401 (auth), 403 (permission), 400 (validation)

Layer 3: Method-level Security (Future)
  @PreAuthorize("hasPermission(...)")
  Optional fine-grained control


3. DATABASE SCHEMA
================================================================================

3.1 CORE ENTITIES
───────────────────

Users Table:
  - id (PK)
  - username (unique)
  - email (unique)
  - first_name, last_name
  - password_hash (from Keycloak usually)
  - is_active
  - created_by, created_at
  - deleted_at, deleted_by (soft delete)

Roles Table:
  - id (PK)
  - role_name (unique): PROFIL_SAISIE, etc.
  - description
  - is_active
  - created_by, created_at
  - deleted_at, deleted_by (soft delete)

Permissions Table:
  - id (PK)
  - permission_name (unique)
  - endpoint (e.g., "/v1/create/partners")
  - http_method (GET, POST, PUT, DELETE)
  - requires_owner_check (true: only own data, false: all data)
  - description
  - is_active
  - created_by, created_at
  - deleted_at, deleted_by (soft delete)

RolePermissions Table (Join):
  - role_id (FK → Roles)
  - permission_id (FK → Permissions)
  - granted_by, granted_at
  - Composite Primary Key: (role_id, permission_id)

UserRoles Table (Join):
  - user_id (FK → Users)
  - role_id (FK → Roles)
  - assigned_by, assigned_at
  - Composite Primary Key: (user_id, role_id)
  - Allows multi-role users

AuditLog Table:
  - id (PK)
  - entity_type (Partner, Transfer, etc.)
  - entity_id (ID of the affected entity)
  - action (CREATE, UPDATE, DELETE)
  - field_name, old_value, new_value
  - changed_by, changed_at

3.2 BUSINESS ENTITIES
──────────────────────

Partners Table:
  - id (PK)
  - name (unique)
  - email (unique)
  - phone
  - address
  - status (active, pending, suspended)
  - created_by, created_at
  - updated_by, updated_at
  - deleted_at, deleted_by (soft delete)

PartnerCurrency Table:
  - id (PK)
  - partner_id (FK)
  - currency (USD, EUR, MAD, etc.)
  - account_number
  - is_active
  - created_at
  - deleted_at (soft delete)

Transfers Table:
  - id (PK)
  - partner_id (FK)
  - amount (decimal)
  - currency
  - status (pending, approved, rejected, completed)
  - reference_number
  - created_by, created_at
  - updated_by, updated_at
  - deleted_at, deleted_by (soft delete)


4. API ENDPOINTS
================================================================================

4.1 AUTHENTICATION
────────────────────

PUBLIC:
  POST /auth/login
    Request: { username: string, password: string }
    Response: { token: string, user: User }
    Status: 200 (ok), 401 (invalid), 400 (validation)

  POST /auth/logout
    Request: empty
    Response: { message: "Logged out" }
    Status: 200

PROTECTED:
  POST /auth/refresh-token
    Response: { token: string }
    Status: 200, 401


4.2 USER MANAGEMENT (Admin only)
──────────────────────────────────

GET /admin/users
  - List all users (paginated)
  - Query params: page, size, sort, filter
  - Response: PaginatedResponse<User>
  - Required permission: MANAGE_USERS

POST /admin/users
  - Create new user
  - Request: UserCreateRequest
  - Response: User
  - Required permission: MANAGE_USERS

GET /admin/users/{id}
  - Get user by ID
  - Response: User
  - Required permission: MANAGE_USERS

PUT /admin/users/{id}
  - Update user
  - Request: UserUpdateRequest
  - Response: User
  - Required permission: MANAGE_USERS

DELETE /admin/users/{id}
  - Delete user (soft delete)
  - Response: { message: "User deleted" }
  - Required permission: DELETE_USERS

GET /admin/users/{id}/roles
  - Get user's roles
  - Response: Role[]
  - Required permission: MANAGE_USERS

POST /admin/users/{userId}/roles/{roleId}
  - Assign role to user
  - Response: { message: "Role assigned" }
  - Required permission: MANAGE_USERS

DELETE /admin/users/{userId}/roles/{roleId}
  - Revoke role from user
  - Response: { message: "Role revoked" }
  - Required permission: MANAGE_USERS


4.3 ROLE MANAGEMENT (Admin only)

  GET /admin/roles

4.5 PARTNER MANAGEMENT (All authenticated users)

7. RUNNING THE BACKEND
================================================================================

PREREQUISITES:
  - Java 17 (or later)
  - PostgreSQL 17 (or compatible)
  - Gradle 8.x

SETUP:
  1. Create PostgreSQL database:
     createdb enrollment_db

  2. Update application.properties:
     spring.datasource.url=jdbc:postgresql://localhost:5432/enrollment_db
     spring.datasource.username=your_db_user
     spring.datasource.password=your_db_password

  3. Build project:
     ./gradlew clean build

  4. Run application:
     ./gradlew bootRun
     
     Or run JAR:
     java -jar build/libs/dlms-enrolment-0.0.1-SNAPSHOT.jar

  5. Verify startup:
     - Check console for "Started DlMsEnrolmentApplication"
     - API available at http://localhost:8080

VERIFY ENDPOINTS:
  - Login: POST /auth/login
  - List users: GET /admin/users (requires ADMIN role)
  - Create partner: POST /v1/create/partners


8. KEYCLOAK INTEGRATION
================================================================================

OAUTH2 CONFIGURATION:
  - Backend acts as OAuth2 Resource Server
  - Validates tokens from Keycloak/Auth Server
  - Extracts user info from JWT claims
  
  spring.security.oauth2.resourceserver.jwt.issuer-uri=<keycloak-url>/realms/bcp

TOKEN STRUCTURE:
  Header: { alg: "RS256", typ: "JWT" }
  Payload: {
    sub: "user-id",
    preferred_username: "john.doe",
    email: "john@example.com",
    realm_access: { roles: ["PROFIL_ADMIN_CENTRAL"] }
  }
  Signature: Signed by Keycloak private key

BACKEND RESPONSIBILITIES:
  1. Validate token signature
  2. Check expiration
  3. Load user from database
  4. Load user's roles and permissions
  5. Enforce RBAC on requests
  6. Audit all changes
