2.4 SOFT-DELETE vs HARD-DELETE EXPLANATION PROVIDED
──────────────────────────────────────────────────────

HARD-DELETE (Standard):
  - Data is permanently removed from database
  - ❌ Cannot recover deleted data
  - ❌ Audit trail broken
  - ❌ Reports missing historical data
  - ✓ Database smaller initially
  - ✗ NOT suitable for banking systems

SOFT-DELETE (Enterprise Grade):
  - Data marked as deleted with timestamp & user
  - ✓ Can recover if needed
  - ✓ Audit trail preserved
  - ✓ Reports include historical deletions
  - ✓ Know WHO deleted WHAT and WHEN
  - ✓ Compliant with banking regulations
  - ✓ GDPR compliance
  - ⚠ Database grows over time

RECOMMENDATION FOR BANKING SYSTEM:
  → SOFT-DELETE (user chose this ✓)

IMPLEMENTATION STRATEGY:
  - Add columns: deleted_at (TIMESTAMP), deleted_by (VARCHAR)
  - Set deleted_at = NOW() and deleted_by = current_user
  - Query always filters: WHERE deleted_at IS NULL
  - Soft-delete cascades to related entities

2.6 MULTI-ROLE SUPPORT DESIGN
──────────────────────────────

USER REQUEST: One user CAN have MULTIPLE roles ✓

IMPLEMENTATION STRATEGY:
  
  When user logs in:
  1. Load User from database
  2. Get ALL roles assigned to user
  3. For EACH role, load ALL permissions
  4. UNION all permissions (most permissive wins)
  5. Store in SecurityContext/Session
  6. On each request, filter by permissions

EXAMPLE:
  User: Ahmed Benali
  Roles: [PROFIL_SAISIE, PROFIL_VALIDATEUR, PROFIL_CONSULTATION]
  
  From SAISIE: [PARTNER_CREATE, PARTNER_UPDATE_OWN, ...]
  From VALIDATEUR: [PARTNER_VALIDATE, REPORT_EXPORT, ...]
  From CONSULTATION: [DOCUMENT_PRINT, ...]
  
  FINAL PERMISSIONS: UNION of all three
  Result: User can do ALL of the above

BENEFIT: User can have different roles for different contexts
  - Morning: Data entry specialist
  - Afternoon: Validation reviewer
  - Evening: System admin

2.8 SECURITY FILTER CHAIN DESIGN
─────────────────────────────────

FILTER ORDER:

1. CorsFilter (if enabled)
2. CsrfFilter (DISABLED for stateless API)
3. JwtAuthenticationFilter [NEW]
   - Extract JWT from Authorization header
   - Validate signature against Keycloak public key
   - Extract username from JWT claims
   - Load User entity from database
   - Create Spring Security Authentication object
   - Set SecurityContext

4. PermissionAuthorizationFilter [NEW]
   - Get current user from SecurityContext
   - Get request endpoint and HTTP method
   - Load user's roles from database
   - Load all permissions for all roles
   - Find matching permission by endpoint + method
   - If permission found:
     - Check if requires_owner_check = TRUE
     - If yes, verify owner (created_by == current_user)
     - ALLOW or DENY
   - If permission not found: DENY (403 Forbidden)

5. OAuth2AuthorizationRequestRedirectFilter
6. SessionManagementFilter
7. ExceptionTranslationFilter
8. FilterSecurityInterceptor (final authorization)


IMPORTANT: Filters are processed sequentially in order.
Each filter can ALLOW, DENY, or PASS to next filter.

  Reason: Data entry users should only modify their own records
  Confirmed by: User ✓
  Benefit: Data isolation, prevents cross-user modification
  Impact: requires_owner_check flag in permission entity
