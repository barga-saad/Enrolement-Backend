1. EXECUTIVE SUMMARY
================================================================================

This document describes the complete Role-Based Access Control (RBAC) system 
for the Partner Enrollment Platform. The system implements:

- 4 Functional Roles (Profiles)
- Dynamic Permission System (Database-driven)
- JWT Authentication via Keycloak
- Custom Authorization Filter
- Soft-Delete Audit Trail
- Multi-Role User Support

Objectives:
✓ Secure REST API with JWT validation
✓ Fine-grained permission control
✓ Maintain complete audit trail
✓ Support multiple roles per user
✓ Stateless and scalable architecture


2. AUTHORIZATION LAYER ARCHITECTURE
================================================================================

2.1 HIGH-LEVEL FLOW

    User Login (Keycloak)
           ↓
    Get JWT Token (Contains: username, email, exp)
           ↓
    Send Request with JWT (Authorization: Bearer <token>)
           ↓
    ┌─────────────────────────────────────────┐
    │ JwtAuthenticationFilter                 │
    │ - Extract token from header             │
    │ - Validate signature against Keycloak   │
    │ - Extract username                      │
    │ - Create SecurityContext                │
    └─────────────────────────────────────────┘
           ↓
    ┌─────────────────────────────────────────┐
    │ PermissionAuthorizationFilter           │
    │ - Load user from database               │
    │ - Get all user roles                    │
    │ - Collect all permissions from roles    │
    │ - Check if endpoint is permitted        │
    │ - ALLOW or DENY request                 │
    └─────────────────────────────────────────┘
           ↓
    ┌─────────────────────────────────────┐
    │ Business Logic (Controller/Service) │
    └─────────────────────────────────────┘
           ↓
    Response to Client


2.2 KEYCLOAK INTEGRATION

- Role: Identity Provider ONLY (Authentication)
- Validates credentials against LDAP
- Issues JWT token after successful login
- Token contains: username, email, issued_at, expires_at
- Backend validates token signature (doesn't validate password)
- Backend DOES NOT use Keycloak roles for authorization
- Authorization is handled 100% by database permissions

6. MULTI-ROLE SUPPORT
================================================================================

6.1 HOW MULTI-ROLE WORKS

Example User with Multiple Roles:

┌───────────────────────────────────────┐
│ User: Ahmed Benali                    │
│ username: ahmed.benali@bcp.com        │
├───────────────────────────────────────┤
│ Assigned Roles:                       │
│ ├─ PROFIL_SAISIE                     │
│ ├─ PROFIL_VALIDATEUR                 │
│ └─ PROFIL_CONSULTATION               │
└───────────────────────────────────────┘

Permissions Resolution:

  1. Load User from Database
  2. Query: SELECT r.id FROM user_roles ur 
           JOIN roles r ON ur.role_id = r.id 
           WHERE ur.user_id = ? AND ur.deleted_at IS NULL
           Result: [SAISIE_ID, VALIDATEUR_ID, CONSULTATION_ID]

  3. Load ALL Permissions for ALL Roles
     Query: SELECT p.* FROM role_permissions rp
            JOIN permissions p ON rp.permission_id = p.id
            WHERE rp.role_id IN (...)
            Result: UNION of all permissions from all 3 roles

  4. Permission Set from SAISIE role:
     - PARTNER_LIST_ALL
     - PARTNER_CREATE
     - PARTNER_VIEW_OWN
     - PARTNER_UPDATE_OWN
     - TRANSFER_CREATE
     - TRANSFER_VIEW_OWN

  5. Permission Set from VALIDATEUR role:
     - PARTNER_VIEW_ALL
     - PARTNER_VALIDATE
     - TRANSFER_VIEW_ALL
     - TRANSFER_VALIDATE
     - REPORT_EXPORT

  6. Permission Set from CONSULTATION role:
     - PARTNER_VIEW_ALL
     - TRANSFER_VIEW_ALL
     - DOCUMENT_PRINT

  7. FINAL PERMISSION SET (Union of all 3):
     - PARTNER_LIST_ALL
     - PARTNER_CREATE
     - PARTNER_VIEW_OWN
     - PARTNER_UPDATE_OWN
     - PARTNER_VIEW_ALL
     - PARTNER_VALIDATE
     - TRANSFER_CREATE
     - TRANSFER_VIEW_OWN
     - TRANSFER_VIEW_ALL
     - TRANSFER_VALIDATE
     - REPORT_EXPORT
     - DOCUMENT_PRINT

6.2 PERMISSION RESOLUTION ALGORITHM

When user requests: PUT /partners/123

Step 1: Get user from JWT token
        Extract: username = "ahmed.benali@bcp.com"

Step 2: Load user and all their roles
        SELECT users, user_roles, roles

Step 3: Load all permissions for all roles
        SELECT permissions WHERE role_id IN (user_role_ids)

Step 4: Check if permission exists
        NEED: PARTNER_UPDATE_OWN for "PUT /partners/{id}"
        HAVE: YES (from SAISIE role)

Step 5: Check owner requirement
        Permission.requires_owner_check = TRUE
        Query: SELECT created_by FROM partners WHERE id = 123
        Check: created_by == "ahmed.benali@bcp.com"
        Result: MATCH ✓

Step 6: GRANT ACCESS ✓

If any step fails → 403 Forbidden


7. SOFT-DELETE IMPLEMENTATION
================================================================================

7.1 SOFT-DELETE STRATEGY

All audit-critical entities use soft-delete:
  - users
  - roles
  - permissions
  - user_roles

Benefits:
  ✓ Audit trail preserved
  ✓ Historical data intact
  ✓ Can restore if needed
  ✓ Regulatory compliance (banking)
  ✓ No orphaned foreign keys

Implementation:

  In Entity:
    @Column(name = "deleted_at")
    private LocalDateTime deletedAt;

    @Column(name = "deleted_by")
    private String deletedBy;

  In Repository (always filter):
    @Query("SELECT u FROM User u WHERE u.deletedAt IS NULL")
    List<User> findAll();

  In Delete Service:
    public void softDelete(User user, String deletedBy) {
        user.setDeletedAt(LocalDateTime.now());
        user.setDeletedBy(deletedBy);
        userRepository.save(user);
        // Cascade: user_roles also soft-delete
    }


7.2 SOFT-DELETE AUDIT TRAIL

Example: User Deletion

8. SECURITY COMPONENTS TO IMPLEMENT
================================================================================

8.1 JWT AUTHENTICATION FILTER

Purpose: Validate JWT token from Keycloak

Flow:
  1. Extract token from "Authorization: Bearer <token>"
  2. Validate signature using Keycloak public key
  3. Check token expiration
  4. Extract username from token claims
  5. Load user from database
  6. Create Spring Security Authentication object
  7. Set SecurityContext

8.2 PERMISSION AUTHORIZATION FILTER

Purpose: Check if user has permission for requested endpoint

Flow:
  1. Get current user from SecurityContext
  2. Get request endpoint and HTTP method
  3. Load user roles from database
  4. Load all permissions for all user roles
  5. Find matching permission (by endpoint + method)
  6. Check if permission exists:
     - If NO → 403 Forbidden
     - If YES → Check requires_owner_check
  7. If requires_owner_check = TRUE:
     - Load entity from database
     - Check created_by == current_user
     - If NO → 403 Forbidden
     - If YES → Allow

8.3 PERMISSION RESOLVER SERVICE

Purpose: Load and cache user permissions

Methods:
  - getUserPermissions(userId) → Set<Permission>
  - getUserRoles(userId) → Set<Role>
  - hasPermission(userId, permissionName) → boolean
  - requiresOwnerCheck(permissionName) → boolean

8.4 AUTHORIZATION SERVICE

Purpose: High-level authorization checks

Methods:
  - canAccessPartner(userId, partnerId) → boolean
  - canValidatePartner(userId, partnerId) → boolean
  - canDeleteUser(userId, targetUserId) → boolean

8.5 AUDIT SERVICE (Optional)

Purpose: Log all sensitive operations

Logs:
  - User login
  - Permission denied
  - Data access
  - Data modification
  - User management
  - Role management

12. EXAMPLE: REQUEST FLOW
================================================================================

SCENARIO: Data Entry User Updates Own Partner Record

Request:
  PUT /partners/42
  Authorization: Bearer eyJhbGc...
  Content-Type: application/json
  {
    "name": "Updated Partner Name",
    "status": true
  }

JWT Token Claims:
  {
    "sub": "5",
    "preferred_username": "ahmed.benali@bcp.com",
    "email": "ahmed.benali@bcp.com",
    "exp": 1711900000
  }

Step-by-Step Processing:

1. JwtAuthenticationFilter
   - Extract: "eyJhbGc..."
   - Validate signature against Keycloak public key
   - Token valid ✓
   - Extract: preferred_username = "ahmed.benali@bcp.com"
   - Load User from DB: id=5, username=ahmed.benali@bcp.com
   - SecurityContext.setAuthentication(new JwtAuthenticationToken(...))

2. PermissionAuthorizationFilter
   - Get current user: User(id=5, username=ahmed.benali@bcp.com)
   - Get endpoint: PUT /partners/{id}
   - Load user roles: [PROFIL_SAISIE]
   - Load permissions for PROFIL_SAISIE:
     [PARTNER_LIST_ALL, PARTNER_CREATE, PARTNER_VIEW_OWN, 
      PARTNER_UPDATE_OWN, TRANSFER_CREATE, TRANSFER_VIEW_OWN]
   - Find permission: PARTNER_UPDATE_OWN ✓ (found)
   - Check requires_owner_check: TRUE
   - Load partner(42) from DB: created_by = "ahmed.benali@bcp.com"
   - Check: created_by == current_user: ✓ MATCH
   - AUTHORIZATION: GRANTED ✓

3. PartnerController.updatePartner()
   - Business logic executes
   - Service updates partner in database
   - Audit log records change

4. Response
   HTTP 200 OK
   {
     "id": 42,
     "name": "Updated Partner Name",
     "status": true
   }

  JwtAuthenticationFilter catches exception
  → 401 Unauthorized (Invalid Token)

Scenario 2: User Not Found in Database
  Request: Valid JWT, but user doesn't exist in DB
  
  PermissionAuthorizationFilter finds: user not in DB
  → 403 Forbidden (User Not Authorized)

Scenario 3: User Lacks Permission
  Request: DELETE /partners (Saisie user has no delete permission)
  
  PermissionAuthorizationFilter checks:
  - Need: PARTNER_DELETE
  - Have: PARTNER_LIST_ALL, PARTNER_CREATE, ...
  - Result: NO MATCH
  → 403 Forbidden (Insufficient Permissions)

Scenario 4: User Trying to Access Someone Else's Record
  Request: PUT /partners/42
  User: ahmed.benali@bcp.com
  Partner 42 created by: fatima.admin@bcp.com
  
  PermissionAuthorizationFilter:
  - Find permission: PARTNER_UPDATE_OWN ✓
  - Check requires_owner_check: TRUE
  - Load partner(42).created_by: fatima.admin@bcp.com
  - Check: fatima.admin@bcp.com == ahmed.benali@bcp.com: ✗ NO MATCH
  → 403 Forbidden (Cannot Access Other User's Records)
